# Vault Search Service 검색 커버리지 실측 검토 — 2026-08-12

## 요약

K_Notes 볼트에서 수행된 "전기차 충전소 설치" 관련 **에이전트 검색 세션**을, 이 플러그인(obsidian-vault-search)의 실제 검색 결과 및 키워드 전수와 3-way로 대조한 검토 기록. 검토는 **읽기 전용**(볼트·플러그인 파일 변경 없음)으로 수행했다.

핵심 발견:

1. **대상 세션은 이 플러그인을 1회도 호출하지 않았다.** Gemini CLI 계열 도구(Glob 2회 → Read 14개 → Grep 1회)만 사용. 플러그인 표준 진입점(`search.ps1` / `vault-search --vault ... search`) 호출 흔적 없음.
2. **세션 결과물 자체는 상위 커버가 양호**: 읽은 14개 파일 중 11개가 플러그인 top-40에 포함. 단, 존재하지 않는 파일(`5_Wiki/entities/업체_휴맥스EV.md`)을 실존 엔티티 페이지처럼 소개하는 오류가 있었고, 회의록·일지·2차 엔티티·행위신고 원본 등은 전부 미읽음.
3. **플러그인 자체의 recall 결함을 실측**: "전기차 충전소 설치" 쿼리에서 `-Top 100`을 요청해도 **57개만 반환**(후보 풀 상한). 키워드(rg) 전수로는 160개 파일이 매치되는데, **회의록 12건·`진행중_업무.md`·주차면수 질의응답(법제처 회답)·`업체_위쥬테크/넥스파/브리츠` 등이 풀에 전혀 진입하지 못함**.
4. **쿼리 변형 민감도가 큼**: 같은 주제라도 `"전기차 충전"`(2토큰) 쿼리는 `"전기차 충전소 설치"`(3토큰) 쿼리에서 탈락했던 질의회신 QA(rank 8)·주차민원 이슈(11)·브리츠테크놀로지(20)·행위신고요청(32)을 상위권에 회수. 반대로 전기 일반 설비 잡음(전기판넬·수배전반·공동전기료 등)은 양쪽 모두 풀 하위권을 차지.

결론: 이 플러그인은 위키 중심 정답 파일(위키 이슈·엔티티·결정·법령) 회수에는 강하지만, **회의록·QA/질의응답·status 문서군과 2차 엔티티, 그리고 짧은 쿼리 변형의 recall이 불안정**하다. 개선 방향의 근거 자료로 사용한다(§5).

## 4. 구조 원인 분석

### 4.1 검색 파이프라인 (`backend/vault_search/search.py` 기준)

1. **토큰화**: `tokenize(query, kiwi)` — Kiwi 형태소 분석.
2. **4개 채널 후보 수집** (각각 상한 존재):
   - `body` BM25: 청크 단위 상위 `bm25_top_k`(30)
   - `heading` BM25 (H1~H3): 상위 `bm25_top_k`(30)
   - `file` (파일명·디렉터리·헤딩 제목 FTS): `_file_candidate_ids`로 파일 단위 후보 → 청크 id 집합
   - `vector`: `vector_index.search(count=vector_top_k)`(30)
3. **RRF 융합**: `weighted_rrf(channels, rrf_k=60)` — body·heading·vector 가중 1.0, file 채널 `title_rrf_weight`(1.0).
4. **최종 선택**: `select_diverse(ranked, rows, requested, max_chunks_per_file=1)` — 파일당 1청크만 유지. `requested = top_k or final_top_k(20)`.
5. **위키 소스 보강**: `expand_wiki_sources` — 조건 충족 시 wiki 소스 1홉 확장(timeline 인텐트에서 rank 31~40 보강용).

**후보 풀 상한**: body(30) ∪ vector(30) ∪ heading/file(대개 부분집합) ≈ **57~60개**가 반환 상한. `-Top 100`이 57개를 돌려준 이유(§3.1). recall 상한은 `bm25TopK`/`vectorTopK`가 결정하며, `maxChunksPerFile`은 풀 구성이 아니라 **최종 선택 단계의 파일 다양성**에만 관여한다.

### 4.2 회의록이 풀에 못 들어가는 이유 (가설, 미검증)

- **(H1) BM25 상한 경합**: `bm25_top_k=30` 청크 상한 안에 "전기차/충전" 매치 밀도가 높은 파일(위키·시설·+ 폴더)이 다수 선점 → 다안건 회의록은 청크당 키워드 밀도가 낮아 30위권 밖.
- **(H2) 벡터 유사도**: 다주제 회의록 청크는 쿼리 임베딩과 유사도가 낮음. paragraph-v1 + 400자 청킹에서도 안건 1개짜리 청크는 주제 일치도가 높아야 하는데, 실측상 0건 → 청킹 품질·임베딩 특성 확인 필요.
- **(H3) 제목 채널 부재**: 회의록 파일명은 `2025년 06월 입주자대표회의 정기 회의 (4기 12차).md` 형태라 "전기차" 관련 제목 토큰이 없어 file 채널 기여 0.

### 4.3 잡음 유입 경로 (가설)

## 5. 개선 제안 (모두 가설 — 실험·벤치마크로 검증 필요)

우선순위순. K_Notes AGENTS.md 검색 워크플로우의 2026-08-11 실측("**후보 풀 크기가 재현율의 지배 변수**", 반환 8→16→24개 시 재현율 46.2%→71.8%→74.4%)과 정합한다.

| ID | 제안 | 근거 | 검증 방법 |
|---|---|---|---|
| **R1** | **후보 풀 확장**: `bm25TopK`/`vectorTopK` 상향(예: 30→60/100) 또는 키워드(rg/Glob) 후보를 별도 채널로 합집합 | §3.2 회의록·QA·status 전멸, §3.1 풀 상한 57 | `search.ps1 -Top 100` 반환 수 및 회의록 진입 여부 재측정; benchmark-guide.md 케이스 추가 |
| **R2** | **쿼리 변형/확장**: 멀티쿼리(짧은 변형 합집합) 또는 복합명사 분해 기반 확장(`충전소→충전/충전기/충전시설/충전구역`, `전기차→전기자동차`) | §3.4: 2토큰 쿼리가 3토큰 쿼리보다 회수 우수 | 동일 케이스에서 쿼리 변형 병합 recall 비교 |
| **R3** | **문서군별 recall 벤치마크 추가**: 회의록·QA/질의응답·status·2차 엔티티를 골드셋에 포함 (이번 검토의 §3.2 목록 활용) | 회의록·status가 전 쿼리에서 0건 | `9_System/scripts/vault-search/benchmarks/` 또는 `backend/tests`에 회귀 케이스 |
| **R4** | **잡음 억제**: 전기 일반 설비 노트(전기판넬·수배전반·공동전기료) 하향 — 도메인/카테고리 가중치, 제목 키워드, BM25 매치 강도 필터 | §3.3: 풀 하위권이 관련 파일 자리 차지 | 정밀도(top-40 내 관련 비율) 전후 비교 |
| **R5** | **top_k > 풀 상한 동작 문서화/경고**: `-Top 100`이 57개만 반환하는 현상을 CLI/문서에 명시하거나 경고 출력 | §3.1: 사용자 오해 소지 | cli.py에 풀 크기 정보 노출 |
| **R6** | **finalTopK 기본값 20 vs 권장 16~40 정합**: 플러그인 UI에 topK 노출, AGENTS.md 권장(16~40 후보 수집) 문서화 | data.json `finalTopK: 20` | settings.md 갱신 |
| **R7** | **3-way 대조 재현 스크립트화**: "세션 결과 vs 플러그인 top-N vs 키워드 전수" 대조를 스크립트로 만들어 이번 검토를 회귀 테스트로 재사용 | 이번 검토가 수작업 3-way 대조 | §6 명령을 `scripts/`로 승격 |

주의: **세션의 결함(플러그인 미사용·휴맥스EV 오류)은 플러그인 문제가 아니라 에이전트 워크플로우 문제**다. 이 문서의 플러그인 개선 대상은 §3~§4의 recall/정밀도/쿼리 민감도 부분이다. 단, "플러그인 top-40에 없던 파일을 glob/grep이 발견했다"(§2.2)는 점은 **키워드 수집과 하이브리드의 상호보완 필요성**을 다시 확인시켜 주며, R1(키워드 채널 병합)의 근거가 된다.

## 6. 재현 절차

```powershell
# 서비스 상태
cd C:\Users\manager\Documents\Obsidian\K_Notes
& .\9_System\scripts\vault-search\search.ps1 -Status

# 플러그인 검색 (top-40 / top-100)
& .\9_System\scripts\vault-search\search.ps1 -Top 40 -Json "전기차 충전소 설치"
& .\9_System\scripts\vault-search\search.ps1 -Top 100 -Json "전기차 충전소 설치"   # → 57개만 반환 확인

# 대조 쿼리
& .\9_System\scripts\vault-search\search.ps1 -Top 40 -Json "전기차 충전"
& .\9_System\scripts\vault-search\search.ps1 -Top 40 -Json "주차관리규정"

# 키워드 전수 (includeGlobs 범위 한정, 9_System 제외)
cd C:\Users\manager\Documents\Obsidian\K_Notes
rg -l -i "전기차|전기자동차|충전소|충전기|충전시설|충전구역|완속충전|급속충전|파워큐브" `
  0_Slip-box 1_Projects 2_Area 3_Resource 4_Archive 5_Wiki "+"

# 회의록 키워드 매치
rg -l -i "전기차|충전" "2_Area\apt\입주자대표회의"

# 휴맥스EV 실존 여부 (세션 오류 재현)
rg -l -i "휴맥스" 2_Area 5_Wiki
```

주의: `rg`는 **경로 인자를 생략하면 stdin 검색 모드**로 들어간다. 이 하네스(pi PowerShell 도구)의 foreground 실행에서는 stdin이 EOF 없는 파이프로 열려 있어, 경로 없는 `rg`는 무한 블로킹 → 타임아웃이 발생한다(2026-08-12 실측, `--debug` 로그에서 `heuristic chose to search stdin` 확인). 반드시 검색 폴더를 명시(`rg ... 2_Area 5_Wiki` 또는 `rg ... .`)할 것. 명시적 경로 시 수백 ms 수준. 백그라운드 태스크는 stdin이 EOF라 빨리 끝나지만 매치 0건(exit 1)으로 나오므로 동일하게 경로를 명시해야 한다.

부차: `9_System/attachments/`에 1.49GB 바이너리(동영상·PDF·zip)가 있어 9_System 포함 전체 스캔은 느리다(실측 9.5s). AGENTS.md대로 `9_System/**`는 제외한다.
